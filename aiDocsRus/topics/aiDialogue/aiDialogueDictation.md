# Потоковая диктовка сообщения пользователя

## Назначение и доступ

`WS /api/ai-dialogue/:id/dictation` принимает аудио с микрофона и возвращает распознанный текст
во время диктовки. Одна сессия WebSocket соответствует одному нажатию «Диктовать» и одной
непрерывной записи. Новый запуск требует нового соединения.

Маршрут обслуживается HTTP-процессом на том же порту, что REST, через библиотеку `ws`.
Это не REST/SSE и не Socket.IO; Orval не генерирует для него функцию подключения.
Существующие конфигурации nginx уже передают WebSocket Upgrade для `/api`.

До HTTP Upgrade сервер проверяет:

1. Точный путь `/api/ai-dialogue/<положительный целый id>/dictation`, без query-параметров.
2. `Origin`: должен совпадать с origin `MainConfigService.get().site.domainRootWithProtocol`.
   Заголовок обязателен; Host и X-Forwarded-Host не используются как источник доверия.
3. Подписанную авторизационную cookie через **тот же экземпляр express-session middleware**,
   что используется REST. Хранилище и настройки сессии остаются общими (Redis).
4. Наличие пользователя в БД, существование диалога и владение им.
5. Отсутствие другой активной диктовки этого пользователя в текущем HTTP-процессе.

При отказе возвращается HTTP 401/403/404/409/500/503 и JSON `{ "code": "..." }`, без Upgrade.
Браузерный WebSocket API не раскрывает тело HTTP-отказа: интерфейс получает событие `error`.
Проверка авторизации ограничена 10 секундами; до её завершения аудио и Soniox не запускаются.
Лимит незавершённых handshake — 32 на процесс. Лимит активных диктовок — 1 на пользователя
на процесс, не распределённая блокировка между репликами сервера.

## Языки и провайдер

Сервер получает из диалога `source_language_code` (изучаемый) и `target_language_code` (родной),
удаляет дубли и открывает `SonioxSttService.openStream` с:

```ts
{
  languageHints: ['en', 'ru'],
  languageHintsStrict: true,
  abortSignal
}
```

При совпадении языков передаётся один код. Параметры языка, модели, API-ключа и таймаутов
клиент не задаёт. Используется стандартная модель адаптера Soniox (`stt-rt-v5`).
Речь на обоих языках сохраняется в транскрипции: это распознавание, а не перевод или исправление.
Строгое ограничение является настройкой модели, а не гарантией фильтрации каждого слова;
особенности смешанной речи и акцентов описаны в
[Soniox Language restrictions](https://soniox.com/docs/stt/concepts/language-restrictions).

## Протокол клиент → сервер

После события WebSocket `open` клиент отправляет JSON:

```json
{ "type": "start", "audioFormat": "auto" }
```

`audioFormat` необязателен, по умолчанию `auto`. В этом режиме отправляется один непрерывный
поток контейнера, включая заголовки, например WebM/Opus от MediaRecorder. Фрагменты — части
одной записи, а не отдельные аудиофайлы. Сервер не перекодирует аудио.

Для сырого аудио поддерживаются `pcm_s16le`, `pcm_f32le`, `mulaw`, `alaw`; обязательны
`sampleRate` (8000–48000) и `numChannels` (1–2). Например:

```json
{ "type": "start", "audioFormat": "pcm_s16le", "sampleRate": 16000, "numChannels": 1 }
```

Для `auto` sampleRate/numChannels передавать нельзя. Неизвестные свойства отклоняются.
Только после ответа `ready` клиент начинает отправлять **бинарные WebSocket-сообщения** с аудио.
Рекомендуются небольшие фрагменты записи, например каждые 100–250 мс, в исходном порядке.
Преобразования Blob → ArrayBuffer должны сохранять этот порядок; следует отслеживать
`WebSocket.bufferedAmount`, чтобы не накапливать бесконечную очередь при медленной сети.

Для нормального завершения:

1. Остановить recorder и дождаться его последнего `dataavailable`.
2. Передать этот последний аудиофрагмент после всех предыдущих.
3. Отправить `{ "type": "stop" }`.
4. Дождаться финальных текстовых событий и `done`; это состояние «Завершаю распознавание…».

`stop` разрешён один раз после `ready`. После него аудио и повторный start/stop запрещены.
Пауза в речи не завершает диктовку автоматически. Событие `cancel` можно отправить на любом
этапе: `{ "type": "cancel" }`; оно отменяет распознавание без ожидания последнего текста.
Закрытие вкладки или WebSocket также немедленно отменяет сессию провайдера.

## Протокол сервер → клиент

Все сообщения — JSON в текстовых WebSocket-сообщениях:

```text
{ "type": "ready" }
{ "type": "partial", "text": "Hello очер" }
{ "type": "partial", "text": "Hello очередь" }
{ "type": "final", "text": "Hello очередь." }
{ "type": "done", "text": "Hello очередь." }
```

- `ready`: соединение с Soniox открыто, можно передавать аудио.
- `partial`: **заменяет весь предварительный хвост**, включая очистку при `text: ""`.
- `final`: **добавляет фрагмент к окончательному тексту** и очищает предварительный хвост.
  Пробелы и пунктуация уже включены провайдером: не вставлять свои пробелы между фрагментами.
- `done`: получено подтверждение `finish()` от Soniox и прочитаны все его события.
  `text` — полный окончательный текст **этой диктовки**, без исходного содержимого textarea.
  Не нужно добавлять его повторно после уже обработанных `final`.
- `cancelled`: отмена подтверждена; окончательный текст не гарантируется, `done` не последует.
- `error`: `{ "type": "error", "code": "AI_DIALOGUE_DICTATION_..." }`.
  После ошибки успешного `done` не будет. Текст внутренних ошибок провайдера клиенту не раскрывается.

После done/cancelled сервер закрывает соединение с кодом 1000. При прикладной ошибке — 1008;
при слишком большом WebSocket-сообщении библиотека может закрыть его с 1009 без JSON ошибки.
При обрыве сети код завершения определяется WebSocket. Если клиент не подтверждает закрытие,
сервер принудительно освобождает сокет через секунду.
При заполненном буфере исходящих данных JSON ошибки может не поместиться: соединение
закрывается с 1008. Отсутствие done всегда означает, что успех диктовки не подтверждён.

## Ограничения и ресурсы

`features/aiDialogue/dictation/aiDialogueDictationProtocol.ts`, `DICTATION_LIMITS`:

- 5 минут на соединение, включая ожидание start и финализацию;
- 10 секунд на start/подключение провайдера, 30 секунд без аудио после ready;
- 256 КиБ на входящее WebSocket-сообщение, 1 МиБ / 64 фрагмента ожидающего отправки аудио;
- 64 МиБ суммарного аудио, 20000 символов распознанного текста;
- 256 КиБ буфера отправки текста в браузер.

Отправки в Soniox выполняются последовательно с ожиданием `sendAudio`. При stop сначала
опустошается очередь принятых фрагментов, затем вызывается `finish()` и ожидается завершение
чтения `events`. Инфраструктурный адаптер дополнительно ограничивает подключение (10 секунд),
отправку фрагмента (15 секунд) и завершение провайдера (30 секунд).

При отмене, ошибке, отключении клиента или `app.close()` вызывается abort провайдера,
освобождаются таймеры и соединения. Автоматического переподключения/повтора аудио нет:
повтор может дублировать текст и расходовать средства. После сбоя пользователь запускает новую диктовку.

Аудио и черновик не сохраняются в БД/R2, не рассылаются через SSE и не создают пользовательское
сообщение или ответ NPC. Проверка грамматики остаётся отдельным REST-запросом
[`aiDialogueMessageCheck.md`](aiDialogueMessageCheck.md).

## Подключение формы

Клиентское подключение реализовано в `face/entities/aiDialogue/dictation/openAiDialogueDictation.ts`
и форме ответа. Браузер использует URL текущего сайта (`ws:` локально, `wss:` при HTTPS),
дожидается ready и начинает запись; cookie передаётся автоматически.
Вставка в реплику/действие, видимое выделение, сохранение окружающего текста, readOnly,
статусы и сброс грамматической проверки описаны в [`aiDialogueForm.md`](aiDialogueForm.md).
Сервер не знает положение курсора.

Обновление названий проверки: метод REST-контроллера теперь `checkAiDialogueUserMessageText`,
operationId — `AiDialogueController_checkAiDialogueUserMessageText`; URL `/check-message` сохранён.

## Файлы и проверки

- `server/src/routes/aiDialogue/aiDialogueDictationWebSocket.service.ts` — upgrade, сессия, Origin, права и лимиты соединений.
- `server/src/features/aiDialogue/dictation/AiDialogueDictationSession.ts` — жизнь диктовки, аудиоочередь, partial/final/stop/cancel.
- `server/src/features/aiDialogue/dictation/aiDialogueDictationProtocol.ts` — протокол, валидация параметров аудио и лимиты.
- `server/src/infrastructure/applyAppSettings.ts` — общий session middleware и подключение к HTTP-серверу.
- `server/src/infrastructure/sonioxStt/` — существующий адаптер Soniox.
- `server/test/aiDialogueDictation.integration.ts` — настоящий HTTP/WebSocket с подписанной cookie;
  провайдер и БД подменены.

```bash
cd server
npm test -- --testPathPatterns='dictation/|aiDialogueDictationWebSocket|aiDialogue.controller|sonioxStt/'
npm run test:ai-dialogue-dictation
```

Unit-тесты покрывают строгие языки и их дедупликацию, валидацию, порядок аудио,
partial/final, ожидание окончания распознавания, отмену, ошибки, таймауты и переполнение очереди.
Интеграционный тест проверяет реальные подписанные cookie (включая испорченную подпись),
Origin, владельца, параллельное соединение, аудио, финализацию и разрыв связи.
Настоящее качество распознавания и совместимость MediaRecorder в целевых браузерах требуют
отдельной проверки с микрофоном и реальным Soniox; автоматические тесты платные запросы не делают.
