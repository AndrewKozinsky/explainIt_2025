# Карта выбора словарной фразы в диалогах

Карта «конкретное вхождение слова → минимальное выражение для словаря» генерируется
в конце того же ответа LLM, что и сюжетные сообщения.
Сначала модель выдаёт обычный построчный текст и переводы: пользователь видит их через SSE chunk.
После всех сюжетных блоков модель дописывает технический раздел wordMaps:.
Сервер разбирает его и сохраняет карты вместе с сообщениями; SSE message и replay уже содержат payload.wordMap.
Подтверждение хода и turnDone происходят после завершения всего потока, включая карту.

Словарь получает только строку слова/выражения, без контекста, переводов или объяснений.
Перевод всего блока остаётся прежним.

## Выражения и клики

Эти правила действуют для всех изучаемых языков (`source_language_code` диалога), а не только для английского.
Английские примеры ниже иллюстрируют общий принцип: выбирать минимальные исходные слова,
которые вместе передают значение нажатого слова в данном предложении.
Для каждого языка модель учитывает его собственные устойчивые выражения и грамматические конструкции;
английские схемы нельзя механически переносить на другие языки.

Карта разреженная: содержит только клики, которым нужен составной словарный запрос.
Остальные слова не требуют записи. Каждый клик рассматривается независимо:

- Do → Do you have;
- you → you (нет записи);
- have → Do you have;
- anything → anything (нет записи);
- to / declare → to declare.

Для
`She put the beautifully wrapped birthday present that she had bought for her sister the day before away in the closet.`
клики по put и away дают только `put away`, без промежуточного объекта и придаточного.
Выражения могут пересекаться и включать несоседние слова. Текст при клике не подсвечивается.
Семантический выбор зависит от модели; примеры в промпте задают ожидаемое поведение.

Например, в немецком `Ich rufe dich an.` клики по `rufe` и `an` выбирают `rufe an`,
а клик по `dich` передаёт только `dich`. Отделяемая приставка связывается с глаголом,
но промежуточные слова в запрос не включаются. В других языках тот же принцип применяется
к связанным словам идиом и конструкций: служебное слово включается в выражение, когда его
отдельный перевод исказит смысл. При этом каждый клик оценивается независимо.
Во всех языках сохраняются исходные формы и порядок выбранных слов; карта не заменяет их
словарной формой и не содержит перевода или грамматического объяснения.

Клик сразу отправляет готовую phrase из карты или само нажатое слово, если записи нет.
Во время стрима, при отсутствии/ошибке карты и в старых сообщениях действует тот же запасной путь.
Позднее появление карты не подменяет предыдущий словарный запрос. Нет ожидания анализа,
надписей о разборе и предложения открыть диалог повторно.
Сообщения пользователя всегда передают только нажатое слово.

## Контракт ответа LLM

После всех обычных блоков и пустой строки:

```text
wordMaps:
{"content":"Do you have anything to declare?","selections":[{"clicked":{"text":"Do","occurrence":0},"words":[{"text":"Do","occurrence":0},{"text":"you","occurrence":0},{"text":"have","occurrence":0}]}]}
```

Один компактный JSON объект на строку для каждой исходной content строки; каждое предложение
в ней анализируется. content точно совпадает с текстом. occurrence — номер вхождения среди слов
с точно таким же написанием в этом блоке, начиная с нуля. Пустые selections допустимы.
Модель не вычисляет символьные offsets и IDs. Переводы, внешность, визуальные описания и заголовки не анализируются.

`splitWordMapFooter` отделяет метаданные до сюжетного парсинга. Клиентское превью также исключает этот раздел.
`attachInlineWordMaps` токенизирует исходный текст через Intl.Segmenter с языком диалога.
Проверяет ссылки на слова, порядок, отсутствие дублей, наличие нажатого слова среди выбранных.
Некорректные записи/строки пропускаются независимо; ошибка карты не вызывает повторную генерацию или turnError.
Связанные слова должны оставаться в своём предложении — это правило промпта.

Для sceneUpdate/help/worldEvent ключ блока `content`; для каждого действия/реплики NPC — `action:<index>`.
Все эти типы получают карту. userActions/userAvoidsNPC исключены.

```ts
{
    status: 'ready',
        blocks
:
    {
        content: {
            content: 'Do you have anything to declare?',
                words
        :
            [{id: 0, text: 'Do', start: 0, end: 2}, /* ... */],
                selections
        :
            [{wordId: 0, wordIds: [0, 1, 2], phrase: 'Do you have'}, /* ... */]
        }
    }
}
```

start/end — UTF-16 offsets в оригинале, end исключительный. phrase строится сервером:
соседние слова сохраняют исходную пунктуацию между ними, несоседние группы соединяются пробелом.
Клиент использует серверные позиции, если content совпадает; иначе сегментирует текст самостоятельно.
Старые pending/failed карты совместимы, но больше не генерируются и не блокируют словарь.
Существующий JSON payload хранит карту без миграций. Новых REST DTO и технических SSE событий нет;
Orval не требуется. Внутренний wordMapRequestId от предыдущей реализации скрывается при чтении старых payload.

## Проверки

Изолированные серверные тесты проверяют перекрытия, разрывные выражения, повторные слова, UTF-16,
все типы сообщений, некорректные карты и сохранение готовой карты до SSE message.
Клиентские (`cd face && npm run test:ai-dialogue`) проверяют немедленный запасной путь,
сохранение текста, скрытие технического раздела при стриме и передачу карты внутри message/replay.
Тесты используют подмены внешних сервисов; реальную семантическую точность модели не оценивают.
