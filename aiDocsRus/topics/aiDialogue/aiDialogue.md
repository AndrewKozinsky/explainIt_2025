# Диалоги с ИИ (AiDialogue)

## Что делает функционал

Ролевой диалог пользователя с LLM на иностранном языке. Пользователь выбирает сценарий (`AiDialogueScenario`) —
например, визит к стоматологу — и в рамках **диалога** (`AiDialogue`)
обменивается с LLM репликами: LLM играет роль NPC (врача, офицера, администратора), ведёт сцену и реагирует на действия
пользователя.

- один сценарий → **много** диалогов (ограничения на пару `(user, scenario)` нет);
- диалог принадлежит **одному** пользователю;
- диалог — контейнер: у него нет текстовых полей, вся переписка хранится в `AiDialogueMessage`;
- **одно событие = одна строка** в `AiDialogueMessage` (реплика, смена сцены, подсказка и т. д.);
- `id` сообщения назначает **сервер** (autoincrement), а не LLM;
- обмен идёт по двум каналам: клиент → сервер через REST (`POST .../messages`), сервер → клиент через постоянный
  SSE-поток (`GET .../stream`).

Сценарии описаны отдельно — см. `aiDocsRus/topics/aiDialogue/aiDialogueScenario.md`. Страница самого диалога
`/dialogues/{dialogId}` (SSE-клиент, стор, рендер событий, форма ввода) — см.
`aiDocsRus/topics/aiDialogue/aiDialoguePage.md`. Существующий SentenceChat к этой фиче отношения не имеет.

## Доменная модель

### `AiDialogue` (контейнер)

| Поле                        | Тип            | Описание                                                    |
|-----------------------------|----------------|-------------------------------------------------------------|
| `id`                        | `Int`          | Первичный ключ (autoincrement)                              |
| `scenario_id`               | `Int`          | FK → `AiDialogueScenario.id`, `onDelete: Cascade`           |
| `user_id`                   | `Int`          | FK → `User.id`, `onDelete: Cascade`                         |

Одна строка = одно событие. Колонка `type` хранит дискриминатор события, `payload` — JSON-тело события **без** поля
`type` (ключи в camelCase).

| Поле          | Тип                          | Описание                                             |
|---------------|------------------------------|------------------------------------------------------|
| `id`          | `Int`                        | Первичный ключ (autoincrement), назначается сервером |
| `dialogue_id` | `Int`                        | FK → `AiDialogue.id`, `onDelete: Cascade`            |
| `type`        | enum `AiDialogueMessageType` | Дискриминатор события                                |
| `payload`     | `String`                     | JSON-тело события (без `type`)                       |
| `created_at`  | `DateTime`                   | Дата создания                                        |

## Статус: что уже сделано

- Таблицы `AiDialogue` (+ колонки `summary`/`summary_up_to`) и `AiDialogueMessage` (миграция
  `20260903151732_add_ai_dialogue_message`).
- REST: создать диалог, список диалогов, удалить диалог, **отправить сообщение** (`POST .../messages`).
- SSE-поток `GET .../stream`: replay истории + подписка на новые события + запуск первого хода.
- Генерация хода LLM (стриминг + построчный парсинг событий), рассылка через in-memory шину.
- Фоновая компакция истории в `AiDialogue.summary` (append-only).
- Клиент: entity-слой `AiDialogue` (list/create/delete), секция «История диалогов», создание по клику на сценарий,
  страница диалога `/dialogues/{dialogId}` и клиентский слой сообщений (см. `aiDocsRus/topics/aiDialogue/aiDialoguePage.md`).
- Языковая модель: сценарий языконейтрален, языки задаются на диалоге (`source_language_code` — практика,
  `target_language_code` — перевод); `title`/`description` сценария — JSON-строки переводов (резолв на клиенте через
  `pickLocalized`).

## REST API

> Все пути ниже — относительны контроллера `@Controller('ai-dialogue')`. Фактический URL — с глобальным
> префиксом `/api/` (задан в `infrastructure/applyAppSettings.ts`: `app.setGlobalPrefix('api')`).
> SSE-соединение клиент открывает по `/api/ai-dialogue/:id/stream`.

Все эндпоинты требуют авторизации (`CheckSessionCookieGuard`).

```
POST   /ai-dialogue                body: { scenarioId, sourceLanguageCode, targetLanguageCode } → 201 AiDialogueOutModel
GET    /ai-dialogue                → 200 AiDialogueOutModel[]
DELETE /ai-dialogue/:id            → 200 boolean
POST   /ai-dialogue/:id/messages   body: CreateAiDialogueMessageInput → 201 AiDialogueMessageOutModel
GET    /ai-dialogue/:id/stream     → SSE (Server-Sent Events)
```

`AiDialogueOutModel`:

```json
{
  "id": 1,
  "sourceLanguageCode": "en",
  "targetLanguageCode": "ru",
  "scenario": {
    "id": 1,
    "slug": "at-the-dentist",
    "title": "{\"en\":\"At the Dentist\",\"ru\":\"У стоматолога\", ...}",
    "description": "{\"en\":\"...\",\"ru\":\"...\"}"
  },
  "createdAt": "2026-09-02T10:41:57.000Z",
  "updatedAt": "2026-09-02T10:41:57.000Z"
}
```

**Обрати внимание:**

- `system_prompt` сценария не попадает в ответ (как и в списке сценариев) — он не отдаётся клиенту.
- `sourceLanguageCode` — язык практики, `targetLanguageCode` — язык перевода (см. «Доменная модель»).
- `scenario.title`/`scenario.description` — сырые JSON-строки переводов; резолвит их клиент через `pickLocalized`.

`AiDialogueMessageOutModel`:

```json
{
  "id": 10,
  "dialogueId": 1,
  "payload": {
    "type": "npcActions",
    "npcId": "...",
    "npcName": "...",
    "npcRole": "...",
    "emotion": "...",
    "actions": [
      {
        "type": "speech",
        "content": "..."
      }
    ]
  },
  "createdAt": "2026-09-03T10:00:00.000Z"
}
```

### Создание диалога

- При создании передаётся `scenarioId` и два языка:
    - `sourceLanguageCode` — язык диалога (тот, который практикует ученик; реплики NPC будут на нём);
    - `targetLanguageCode` — язык перевода (родной язык ученика; для текстовых полей LLM добавляет `translation`).
- Сценарий должен существовать (иначе `404` `AI_DIALOGUE_SCENARIO_NOT_FOUND`).
- Начать диалог можно только по **публичному** (`user_id === null`) или **своему** сценарию (иначе
  `403` `USER_IS_NOT_OWNER`).
- Повторные вызовы создают новые диалоги.

Языки берутся из диалога, а не из сценария — сценарий языконейтрален (см. `aiDocsRus/topics/aiDialogue/aiDialogueScenario.md`). На
клиенте `sourceLanguageCode` пока временно захардкожен как `'en'` (см. `useAiDialogueScenarioClick`).

### Удаление диалога

- Проверяются существование (`404` `AI_DIALOGUE_NOT_FOUND`) и владение (`403` `USER_IS_NOT_OWNER`).
- Возвращает `true` (каскадно удаляются и сообщения).

### Отправка сообщения (действие пользователя)

`POST /ai-dialogue/:id/messages` — единственный канал «клиент → сервер». Клиент может отправить только событие
пользователя (`CreateAiDialogueMessageInput`):

```ts
type CreateAiDialogueMessageInput =
    | { type: 'userActions'; actions: AiDialogueActionItem[] }   // действия и реплики пользователя
    | { type: 'userAvoidsNPC' }                                   // пользователь ушёл от разговора
```

Хендлер проверяет существование и владение диалога, затем:

1. Если для диалога уже идёт генерация (`generationAlreadyActive`) — возвращает
   `400` `AI_DIALOGUE_GENERATION_ALREADY_ACTIVE` (нельзя действовать, пока NPC отвечает).
2. Иначе сохраняет сообщение и **fire-and-forget** запускает генерацию ответа (результат доедет через SSE).

## События диалога

Дискриминированный union `AiDialogueEvent` (в `types/aiDialogueMessage.ts`). `type` — дискриминатор.

| `type`          | Поля                                                | Кто генерирует |
|-----------------|-----------------------------------------------------|----------------|
| `sceneUpdate`   | `content: string`, `translation`                    | LLM            |
| `npcActions`    | `npcId`, `npcName`, `npcRole`, `emotion`, `actions` | LLM            |
| `help`          | `content: string`, `translation`                    | LLM            |
| `worldEvent`    | `content: string`, `translation`                    | LLM            |
| `userActions`   | `actions`                                           | клиент         |
| `userAvoidsNPC` | —                                                   | клиент         |

`actions` — массив `AiDialogueActionItem = { type: 'action' | 'speech'; content: string }` (`action` — невербальное
действие, `speech` — реплика).

Событие `help` — это не перевод и не повторение реплики NPC. LLM создаёт его только тогда, когда пользователю может быть
непонятно, какое действие совершить дальше, и NPC не дал ясную прямую инструкцию. Если NPC уже задал прямой вопрос или
попросил о конкретном действии, дополнительный `help` не создаётся. Например, после стука в дверь можно отправить `help`
с предложением открыть дверь, но после реплики NPC «Какой абонемент вы хотите купить?» такой
`help` будет дублированием и не нужен.

Сервер **сам** никогда не генерирует `userActions`/`userAvoidsNPC` от имени пользователя — эти два типа выделены в
отдельный тип `AiDialogueClientEvent`.

Событие `userAvoidsNPC` означает «пользователь ушёл от текущего NPC». LLM должен отреагировать на уход (текущий NPC
прощается или уточняет, не продолжая прежнюю просьбу) и затем представить другого NPC, уместного по сцене, чтобы ученик
мог продолжить практику. Персонажей LLM придумывает сам, исходя из сценария (правила — в
`buildAiDialoguePrompt`).

## SSE-протокол

`GET /api/ai-dialogue/:id/stream` — постоянное соединение (открывается один раз при открытии страницы диалога). Каждый
фрейм — `MessageEvent`, `data` которого — `AiDialogueStreamEvent`:

```
{ "type": "message",  "message": DialogueServerMessage }   // одно сохранённое сообщение
{ "type": "chunk",    "chunk": "..." }                     // сырой фрагмент ответа LLM (превью)
{ "type": "turnStarted" }                                  // началась генерация хода (до первого chunk)
{ "type": "turnReset" }                                    // повторная попытка генерации началась
{ "type": "turnDone" }                                     // ход завершён (успех или ошибка)
{ "type": "turnError","error": "..." }                     // ход не удался
```

- `message` — используется и для **replay** истории (при подключении), и для новых событий. Обёртка
  `DialogueServerMessage = { id, dialogueId, createdAt, payload }`.
- `chunk` — сырой фрагмент ответа LLM. Клиент собирает из него превью построчным парсером (`parseAiDialoguePreview`);
  авторитетный разбор делает сервер (`parseAiDialogueEvents`) в конце стрима.
- `turnStarted` — сервер начал генерацию хода (до первого `chunk`). Клиент показывает «ответ готовится».
- `turnReset` — сервер начал повторную попытку генерации после провала парсинга. Клиент сбрасывает накопленное превью
  (`accumulated` и `preview`), но `isGenerating` остаётся `true`.
- `turnDone` — сигнал, что можно снова действовать (после каждого хода, даже при ошибке).

### Порядок при подключении

1. Клиент открывает SSE-соединение.
2. Сервер проверяет существование и владение диалога.
3. Подписывается на in-memory шину диалога (чтобы ловить события параллельной генерации).
4. Отдаёт **replay** всех сохранённых сообщений (дедуп по `id` — события, уже пришедшие через шину, не повторяются).
5. Если диалог «ждёт хода» (см. ниже) — запускает генерацию первого ответа.

Соединение не закрывается по завершении хода — оно живёт, пока открыта страница.

## Схема обработки (CQRS)

`AiDialogueController` вызывает через `CommandBus`:

- `CreateAiDialogueCommand` → проверка сценария → `AiDialogueRepository.createDialogue` →
  `AiDialogueQueryRepository.getDialogueById`.
- `GetUserDialoguesCommand` → `AiDialogueQueryRepository.getUserDialogues`.
- `DeleteAiDialogueCommand` → проверка владения → `AiDialogueRepository.deleteDialogueById`.
- `CreateAiDialogueMessageCommand` → проверка существования/владения → запрет при активной генерации →
  `AiDialogueMessageRepository.createMessage` → `AiDialogueQueryRepository.getMessageById` → fire-and-forget запуск
  `GenerateAiDialogueTurn`.

SSE-эндпоинт не использует CQRS: контроллер напрямую подписывается на `AiDialogueSseHub` и вызывает
`GenerateAiDialogueTurn.triggerIfNeeded`.

## Генерация хода (`GenerateAiDialogueTurn`)

Сервис `features/aiDialogue/GenerateAiDialogueTurn.service.ts`. Один «ход» = один вызов LLM, который может вернуть
**несколько** событий (плоским построчным текстом, см. «Стриминг и формат ответа»).

### Когда генерировать («ждёт ли диалог хода»)

Детерминированное правило в `shouldGenerateTurn`:

- сообщений нет → генерировать;
- последнее сообщение — событие пользователя (`userActions`/`userAvoidsNPC`) → генерировать;
- иначе (последнее — событие LLM) → ждать действия пользователя.

### Процесс `generate(dialogueId)`

1. Guard: если для диалога уже идёт генерация — выход (идемпотентно). Иначе регистрирует
   `AbortController` в `ActiveAiDialogueGenerationRegistry` (лимит — **1 активная генерация на диалог**).
2. Читает диалог (нужен `summary`, `summary_up_to`, `scenario_id`) и сценарий.
3. Читает все сообщения; «свежие» события = сообщения с `id > summary_up_to`.
4. Собирает промпт через `buildAiDialoguePrompt` (system = `system_prompt` сценария + строгий построчный контракт
   ответа + реестр NPC + правила языка; user = текущая сцена + сжатая история + свежие события). Язык диалога берётся из
   `source_language_code`, язык перевода/подсказок — из `target_language_code`.
5. Стримит ответ: `LlmAdapterService.stream({ responseFormat: 'text' })`, накапливает текст и рассылает сырые `chunk`
   -события в шину.
6. В конце парсит накопленный текст через `parseAiDialogueEvents` («спасающий» построчный разбор — недостающий
   `translation` хвостового блока подставляется как `''`, битые блоки отбрасываются). Если не удалось спасти ни одного
   события — повторный вызов LLM (до `MAX_PARSE_ATTEMPTS` = 2) с корректирующей подсказкой; между попытками клиенту
   шлётся `turnReset`. Если и повтор не удался — ошибка `cannotParseLlmResponse`.
7. Каждое событие сохраняет (`createMessage`) и рассылает как `message`.
8. В `finally`: снимает регистрацию в registry и рассылает `turnDone`.
9. После хода (уже вне registry) fire-and-forget вызывает `SummarizeAiDialogue.summarizeIfNeeded`.

Ошибки не роняют поток: в `catch` рассылается `turnError`, затем всё равно `turnDone`.

### Стриминг и формат ответа

LLM отвечает **плоским построчным текстом** (`responseFormat: 'text'`), а не JSON — так контент реплики стримится
обычными строками и рисуется на клиенте посимвольно. Один ход = один или несколько блоков, разделённых **ровно одной
пустой строкой**; блок = строка-заголовок + поля по одной строке.

```
npcActions|<npcId>|<npcName>|<npcRole>|<emotion>
action:
<описание действия>
<перевод>
speech:
<реплика>
<перевод>
```

```
sceneUpdate
<описание новой сцены>
<перевод>
```

Заголовки текстовых событий — `sceneUpdate`, `help`, `worldEvent` (без полей, затем `content` и
`translation`). Внутри `npcActions` повторяются тройки `метка:` / `content` / `translation`, где метка —
`action:` или `speech:`. `translation` присутствует **всегда** (`targetLanguageCode` обязателен). «Ничего не говорить» →
пустой ответ.

Сырые чанки отдаются клиенту для превью (толерантный построчный разбор `parseAiDialoguePreview`), а **авторитетный
разбор** событий делает сервер на полном накопленном тексте (`parseAiDialogueEvents`). По умолчанию используется
DeepSeek (`DEFAULT_FLASH_AI_MODEL`) — выбор модели клиентом не реализован.

### Реестр активных генераций

`ActiveAiDialogueGenerationRegistry` — `Map<dialogueId, AbortController>`. В отличие от SentenceChat (лимит на
пользователя), здесь лимит **на диалог**. `AbortController` зарезервирован под будущую отмену: сейчас генерация не
привязана к жизни SSE-соединения (она продолжается и при отключении клиента, т.к. результат пишется в БД).

### In-memory шина (`AiDialogueSseHub`)

`Map<dialogueId, Subject<MessageEvent>>`. SSE-эндпоинт подписывается на `Subject` своего диалога, а генерация пушит
события в него. Благодаря этому события, порождённые POST-запросом (в другом HTTP-запросе), доезжают до уже открытого
SSE-соединения. Субъекты не вычищаются (диалогов немного, `Subject` пустой).

## Компакция истории (`SummarizeAiDialogue`)

Чтобы не переполнять контекст LLM, давние события сжимаются в `AiDialogue.summary`. Сводка — **append-only**
массив блоков, сериализованный в JSON-строку (колонка `TEXT`):

```json
[
  {
    "state": {
      "scene": "...",
      "activeNpcId": "...",
      "roster": [
        {
          "npcId": "...",
          "npcName": "...",
          "npcRole": "..."
        }
      ]
    },
    "history": "краткий пересказ"
  }
]
```

### Правила

- **Триггер**: когда несжатых сообщений (`id > summary_up_to`) набралось больше `SUMMARIZE_WHEN_UNCOMPRESSED_GT`
  (= 20) — сжать всё, кроме последних `KEEP_UNCOMPRESSED` (= 5).
- **`history`** (текст пересказа) генерирует LLM через `buildSummaryPrompt` + `LlmAdapterService.generate`
  (обычный текст, не JSON).
- **`state`** (сцена / активный NPC / реестр NPC) сервер выводит **детерминированно** через
  `deriveAiDialogueState` — не полагаясь на LLM. `roster` собирается из `npcActions`, `scene` — из последнего
  `sceneUpdate`, `activeNpcId` — `npcId` последнего `npcActions`.
- **Новый блок** добавляется только при изменении `state` (`sameAiDialogueState`); иначе новый `history`
  дописывается в `history` последнего блока.
- `summary_up_to` сдвигается на `id` последнего сжатого сообщения.

Выполняется в фоне после завершения хода (не блокирует клиента и не занимает registry), защита от параллельного
запуска — `Set` `inFlight`. Ошибки компакции только логируются.

## Как работает клиент

### Entity-слой

Повторяет структуру `entities/aiDialogueScenario`:

- `AiDialogueRepository` — тип `AiDialogueModel` (`id`, вложенный `scenario`, `sourceLanguageCode`,

Ключ кэша запроса списка — `['ai-dialogue', 'list']`. `scenario.title`/`scenario.description` — сырые JSON-строки,
резолв под локаль — через `pickLocalized` (см. `aiDocsRus/topics/aiDialogue/aiDialogueScenario.md`).

### Создание диалога по клику на сценарий

1. Если пользователь не вошёл (`useUser()` → `null`) — `LoginPromptModal`.
2. Иначе `aiDialogueService.createDialogue({ scenarioId, sourceLanguageCode, targetLanguageCode })`.
    - `sourceLanguageCode` — пока временно `'en'` (захардкожено, с TODO);
    - `targetLanguageCode` — текущая локаль интерфейса (`locale`).
3. При успехе инвалидируется кэш списка и выполняется `router.push` на `pageUrls.aiDialogues.dialog(dialog.id)`.

## Ошибки

Ключи из `errorMessage.aiDialogue`:

- `notFound` — диалог не найден (`404`).
- `scenarioNotFound` — сценарий не найден при создании диалога (`404`).
- `generationAlreadyActive` — для диалога уже идёт генерация (`400`), нельзя отправить действие пользователя.
- `cannotParseLlmResponse` — не удалось разобрать ответ LLM в события (`500`, уходит в `turnError`, а не роняет SSE).

Плюс `user.isNotOwner` (`403`) при доступе к чужому диалогу.

## Вне объёма (следующие шаги)

- Отмена генерации пользователем (задействовать `AbortController` в registry) и выбор LLM-модели клиентом.
- Выбор языка практики пользователем: сейчас `sourceLanguageCode` при создании диалога захардкожен как `'en'`.

### Цель и границы

Основная задача приложения — практика иностранного языка через общение с ИИ. Аватары и иллюстрации помогают
погружению в ситуацию, но остаются второстепенными: их подготовка, ошибки и отсутствие не блокируют разговор.

Согласованные требования:

- У пользователя есть выбранный комплект аватаров. Сначала доступны два готовых образа — мужской и женский.
  Модель данных позволяет расширять каталог и впоследствии добавлять личный образ из загруженного изображения.
- NPC могут быть любыми и появляются динамически после начала диалога. Заранее заданный состав персонажей не требуется.
- Внешность NPC создаётся при его первом появлении в конкретном диалоге. Первый NPC обрабатывается так же, как остальные.
  Общий аватар первого NPC на уровне сценария больше не является требованием: разные диалоги одного сценария
  могут содержать персонажей с разной внешностью.
- Уже появившийся NPC сохраняется в реестре этого диалога. При возвращении используется его прежний комплект.
- Около реплик пользователя и NPC показываются их аватары с выражением лица, выбранным по коду эмоции.
- Эмоции определяет ИИ. Дополнительных элементов управления эмоциями для пользователя нет.
- Иллюстрации генерируются **только по событиям смены сцены `sceneUpdate`**. Появление NPC, изменение эмоции,
  завершение встречи или `worldEvent` сами по себе не запускают генерацию иллюстрации.
- Аватары и сцены имеют общий художественный стиль. Референсы помогают сохранять узнаваемость, но небольшие
  различия внешности между изображениями допустимы. Проверки точного сходства лиц и перегенерации ради него не нужны.
- Смена выбранного образа пользователя меняет его аватары возле реплик во всех диалогах. Готовые сцены не перегенерируются.
- Все изображения сохраняются в Cloudflare R2.
- Стоимость генераций не учитывается: не нужны расчёт расходов, финансовые квоты, бюджеты или ограничения по стоимости.
  Технические лимиты провайдера, ограничение параллельных запросов и конечное число попыток нужны для надёжной работы.

### Сценарий, диалог и персонаж

Сценарий задаёт исходную ситуацию и правила общения. Он может описывать встречу с конкретным стоматологом,
нахождение в лесу или на площади. Генерация внешности не требует заранее заданного персонажа в сценарии.
Это правило одинаково для публичных и будущих личных сценариев; доступ к личному сценарию и его диалогам остаётся
ограничен владельцем. Создание личных сценариев — отдельная функциональность, не обязательная для внедрения изображений.

«Сохранённый персонаж» означает запись NPC **внутри конкретного диалога**, а не общего персонажа всех сценариев.
Между диалогами автоматически переиспользуются только готовые пользовательские образы и эталоны стиля.

У NPC обязательны стабильный идентификатор и краткое описание внешности, достаточное для генерации портрета.
Имя, роль и биография не обязательны. Допустим персонаж «незнакомец в плаще» без дополнительной истории.
Если сценарий задаёт имя или внешность, ИИ учитывает эти сведения при первом появлении NPC.

Для идентичности используется пара `(dialogueId, npcId)`. Имя и профессия не являются ключами: два администратора
могут быть разными людьми. ИИ получает реестр и при повторной встрече возвращает прежний `npcId`.
Сервер проверяет идентификаторы и создаёт запись нового персонажа один раз. При повторном появлении нельзя
перезаписывать его внешность случайно изменившимся описанием LLM.

Реестр хранится отдельно от переписки и `summary`. Компакция сохраняет ссылки на NPC, но не является источником
их изображений и внешности. Завершение встречи по инициативе пользователя или NPC не удаляет персонажа:
он может появиться снова. Завершение встречи и завершение всего диалога следует различать; изображение не
определяет ни одно из этих состояний.

### Образ пользователя и единый стиль

Готовый пользовательский образ — комплект, содержащий основной нейтральный портрет, изображения эмоций
и при необходимости дополнительные референсы. Пользователь хранит ссылку на выбранный комплект, а не значение
enum «мужской/женский». Несколько пользователей могут использовать один общий комплект без повторной генерации.

Стиль задаётся версионируемым набором эталонных изображений и кратким текстовым описанием: характер линий,
палитра, освещение, пропорции и детализация. Набор должен показывать портрет и сцену, чтобы описывать не только лица,
но и окружение. Конкретный художественный стиль предстоит выбрать перед подготовкой материалов.

Основной портрет служит исходным референсом для эмоций и дополнительных ракурсов. Не следует строить цепочку,
в которой каждое новое выражение создаётся из предыдущего: это может накапливать изменения внешности.

Дополнительные ракурсы поддерживаются моделью данных и генерируются при необходимости: анфас, профиль,
три четверти, вид сзади, фигура. Подготовка всех ракурсов для каждого случайного NPC не обязательна.
Не нужно генерировать декартово произведение всех эмоций и ракурсов. Для аватаров достаточно одного согласованного
кадрирования с разными выражениями, для сцен используются доступные референсы.

При генерации сцены передаются эталон стиля, основные портреты пользователя и присутствующих NPC,
а также описание ситуации. Дополнительные референсы помещения и ракурсов используются при наличии.
Каждому изображению в запросе задаётся понятная роль. Предыдущая сцена может дополнять портреты, но не заменяет их.

### Эмоции

Используется общий фиксированный словарь кодов. Предлагаемый начальный набор:

`neutral`, `happy`, `sad`, `angry`, `surprised`, `confused`, `worried`, `embarrassed`,
`thoughtful`, `skeptical`, `relieved`, `encouraging`.

Окончательный набор следует зафиксировать до генерации готовых комплектов. Названия в интерфейсе могут переводиться,
ключи изображений остаются одинаковыми независимо от языка практики и интерфейса.

ИИ возвращает код эмоции при генерации ответа. Для блока реплик используется последняя возвращённая для него
эмоция; сложная модель смены эмоций внутри `actions` не требуется. Отдельные сохранённые сообщения используют
собственную эмоцию: новая реплика не меняет выражение у прошлых сообщений.

Эмоцию пользователя ИИ определяет по контексту после отправки действия или реплики. Для этого он может вернуть
отдельную визуальную метаинформацию со ссылкой на исходное пользовательское сообщение. Она не является новым
`userActions`, не добавляет выдуманный пользовательский текст и не меняет смысл отправленного сообщения.
Точный формат этой метаинформации предстоит добавить в контракт генерации и парсер.

Нормализация кодов и выбор изображения выполняются сервером/клиентом детерминированно. Неизвестное значение
приводится к `neutral`. При отсутствии нужного изображения используется нейтральный портрет того же образа.
Если основного портрета ещё нет, отображается общая заглушка.

У пользователя нет ручного выбора эмоции и подтверждения автоматической оценки. Его сообщение появляется сразу
с нейтральным аватаром; после получения эмоции изображение может обновиться.

В сообщениях пользователя хранится код эмоции, а образ разрешается через текущий выбор пользователя.
Смена выбранного комплекта обновляет аватары всей истории, включая открытые диалоги и кэш клиентских данных.
В сценах сохраняется конкретный комплект и его версия на момент постановки задания.

### Подготовка нового NPC

1. После подтверждённого появления NPC сервер сохраняет его запись и описание внешности.
2. Текст NPC сразу отправляется клиенту. До готовности портрета показываются доступное имя/описание и заглушка.
3. В очередь ставится генерация основного нейтрального портрета с эталоном стиля.
4. Портрет сохраняется в R2, затем обновляются аватары реплик этого NPC.
5. На основе основного портрета в фоне готовятся изображения эмоций. Нужная сейчас эмоция имеет приоритет.
6. При повторной встрече используются готовые изображения или существующие задания; повторное создание комплекта не требуется.

Сначала требуется основной портрет, затем зависимые изображения. Приоритеты определяют порядок работы,
но фоновые задания не блокируют генерацию текста и ввод пользователя.

### Сцены и момент генерации

Каждое сохранённое `sceneUpdate` создаёт снимок сцены и одно намерение сгенерировать иллюстрацию.
Начальная иллюстрация появляется только при наличии начального `sceneUpdate`.

Снимок содержит идентификатор исходного сообщения, описание ситуации, присутствующих участников,
ссылки на их комплекты, версию стиля и необходимые сведения о позах, одежде и предметах.
Описание иллюстрации фиксирует уже произошедший момент и не придумывает дальнейшее развитие разговора.

Свободного `content` может быть недостаточно для определения состава участников. Контракт генерации должен
передавать визуальное состояние сцены или отдельный сервис должен извлекать его из подтверждённого контекста.
Состав сцены нельзя брать из «последнего активного NPC» в момент выполнения worker: к этому времени диалог
может перейти к другим персонажам. Если в одном ходе `sceneUpdate` предшествует представлению NPC, снимок
собирается с учётом относящихся к нему событий подтверждённого хода; следующая сцена завершает этот диапазон.

На иллюстрации изображаются пользователь и присутствующие персонажи; сцена без NPC допускает одного пользователя.
Задание может ждать основных портретов участников. Ошибка зависимости не приводит к бесконечному ожиданию:
после исчерпания попыток сцена получает ошибку, текстовый диалог продолжается.

Изображение прикрепляется к конкретному `sceneId` и версии. Если во время генерации появилась другая сцена,
готовый результат добавляется к своему событию в истории и не заменяет текущую иллюстрацию.
Готовые сцены неизменяемы при смене пользовательского аватара или последующем обновлении описания персонажа.

### Предлагаемая модель хранения

| Сущность | Назначение |
|----------|------------|
| `AiDialogueVisualStyle` | Версия стиля, описание и ссылки на эталоны |
| `AvatarSet` | Общий или личный пользовательский комплект, основной портрет, описание, версия стиля и доступность |
| `User.avatar_set_id` | Текущий выбранный пользовательский комплект |
| `AiDialogueCharacter` | NPC конкретного диалога: `npcId`, описание внешности, необязательные имя/роль, основной портрет и стиль |
| `AiDialogueScene` | Снимок сцены, исходное `sceneUpdate`, участники и зафиксированные версии образов |
| `AiDialogueMessageVisual` | Визуальные метаданные сообщения, прежде всего вычисленная эмоция пользователя |
| `ImageAsset` | Конкретное изображение: назначение, владелец/объект, эмоция или ракурс, ключ R2, MIME, размеры, версия |
| `ImageGenerationJob` | Сохранённое задание: тип, входные данные, зависимости, статус, попытки, провайдер, модель, результат/ошибка |
| `ImageGenerationOutbox` | Надёжная передача намерения генерации из транзакции PostgreSQL в очередь |

Это логические обязанности; реализация может объединить таблицы, если связи и ограничения остаются явными.
Отдельные универсальные сущности биографии, идентичности и участия NPC не обязательны для данной задачи.

Нужны уникальные ограничения на `(dialogue_id, npc_id)`, снимок исходного события сцены и вариант изображения
`(владелец комплекта/персонажа, версия, назначение, эмоция/ракурс)`. Эти ограничения предотвращают дубли при
повторных запросах и конкурентной обработке. Внешние идентификаторы LLM проверяются в области текущего диалога.

Вход задания фиксируется при его создании: выбранный образ пользователя, NPC, стиль, текст и параметры генерации.
Worker не подменяет их текущими значениями. Для задания, ожидающего новый портрет NPC, сохраняется зависимость
на конкретный основной портрет, которая разрешается после его готовности.

### Очередь, восстановление и провайдеры

Использовать существующие BullMQ, Redis и отдельный worker. Новые producer/processor размещаются по аналогии
с очередью генерации субтитров. Статусы `queued`, `generating`, `ready`, `failed` сохраняются в БД;
ожидание зависимостей отражается отдельно от активного вызова провайдера.

В транзакции сохраняются исходное событие/снимок, задание и запись outbox. Диспетчер надёжно передаёт задание
в BullMQ; повторная доставка безопасна. Только `fire-and-forget` из HTTP-процесса недостаточен, поскольку
перезапуск может потерять намерение генерации.

Генерация запускается только из подтверждённых событий, не из SSE `chunk` и клиентского превью.
`turnReset` и повтор парсинга не создают изображения для отброшенного ответа. Обработка изображений не занимает
`ActiveAiDialogueGenerationRegistry`, а `turnDone` остаётся сигналом завершения текстового хода.

У заданий ограничены параллельность, время выполнения и число попыток. Для временных ошибок используются
повторы с задержкой, для заведомо неверного ввода — конечная ошибка. Если провайдер вернул идентификатор запроса
или URL проверки состояния, они сохраняются: после перезапуска worker сначала проверяет существующий запрос.
При неопределённом результате тайм-аута не следует безусловно создавать новый внешний запрос.

Проверяются пригодность ответа, возможность декодирования файла, MIME и размеры. Автоматическая проверка
точного сходства лиц не входит в требования. Результат считается готовым после сохранения файла в R2
и записи метаданных в БД. Сбои между этими действиями обрабатываются повторно безопасно.

Предусмотреть небольшой адаптер генератора изображений. Он принимает описание, референсы и параметры,
возвращает готовый файл либо внешний запрос, за которым можно наблюдать. Конкретные асинхронные механизмы
инкапсулируются в адаптере. Провайдер и модель сохраняются в задании.

Кандидаты: FLUX 3 Image от BFL, OpenAI GPT Image и Comfy API с размещённым workflow.
Генерация выполняется внешним сервисом; собственный GPU-сервер не требуется. Конкретный провайдер пока не выбран.
Перед подключением проверить актуальный API и сравнить пригодность результатов на выбранном стиле:
эмоции, несколько персонажей в кадре, смена позы, повторная встреча. Проверка не требует системы учёта стоимости.
Автоматическое переключение провайдеров не обязательно и может нарушить визуальный стиль.

### SSE, REST и клиент

Технические уведомления о картинках передаются отдельными SSE-событиями, например `visualAssetUpdated`,
с указанием объекта, статуса и версии. Это не строки сюжетной переписки `AiDialogueMessage`:
они не участвуют в `shouldGenerateTurn`, промпте текстового ответа или компакции.

Визуальная метаинформация пользовательского сообщения сохраняется отдельно и приходит обновлением
со ссылкой на `messageId`. Точный состав REST DTO и SSE union определяется при реализации;
изменения отражаются в серверных/клиентских типах, OpenAPI и генерации Orval.

Нынешняя `AiDialogueSseHub` находится в памяти HTTP-процесса. Worker передаёт уведомления через Redis
или другой межпроцессный канал, а HTTP-процесс отправляет их в SSE соединения владельца диалога.
БД остаётся источником состояния. При загрузке страницы и переподключении клиент получает актуальные
визуальные данные через REST или отдельный SSE-снимок после подписки; потерянное уведомление не теряет результат.
Обновления имеют версию, чтобы позднее старое событие не перезаписало новое состояние.

Клиент хранит визуальные данные отдельно от массива сюжетных сообщений и `isGenerating`.
Нейтральные изображения и заглушки обеспечивают немедленное отображение. Готовая эмоция или портрет
обновляет связанные сообщения без повторного создания реплик.

Иллюстрация размещается возле соответствующего `sceneUpdate`. Размер места под изображение резервируется,
чтобы поздняя загрузка не вызывала резких скачков переписки. Изображения не закрывают форму ответа,
переводы и словарь. Ошибка картинки показывается локально и не становится `turnError`.

### R2, доступ и удаление

В R2 сохраняются эталоны стиля, основные портреты, эмоции, дополнительные референсы и сцены.
Для интерфейса подготавливаются необходимые размеры. В БД хранится ключ объекта, а не истекающая подписанная ссылка;
URL выдаётся при чтении с учётом прав доступа.

Готовый общий каталог и эталоны могут переиспользоваться всеми пользователями. Личные изображения,
NPC и сцены конкретного диалога доступны его владельцу. Проверка доступа выполняется также для
визуальных REST эндпоинтов и уведомлений SSE.

Удаление диалога прекращает его задания и удаляет его личные визуальные данные. Worker перед публикацией
результата проверяет, что объект ещё существует; поздний результат не восстанавливает удалённый диалог.
Удаление файлов из R2 выполняется надёжно с повторами. Общие комплекты, эталоны и пользовательский образ,
который применяется в других диалогах, при этом не удаляются.

Смена пользовательского комплекта не удаляет старые файлы, пока на них ссылаются готовые сцены или задания.
Версии материалов сохраняются неизменяемыми; смена стиля не запускает массовую перегенерацию старой истории.

### Будущая загрузка собственного изображения

Сейчас требуется заложить поддержку личных комплектов в модель; интерфейс загрузки реализуется отдельным этапом.
Согласованное будущее поведение:

1. Проверить тип, размер и возможность декодирования файла.
2. Проверить содержимое изображения: оно должно содержать подходящего для аватара человека/персонажа.
   Дом, пейзаж и изображение без подходящего персонажа отклоняются с понятной ошибкой.
   Неоднозначный вход, например группа людей без выделенного персонажа, также отклоняется.
3. Для подходящего изображения создать стилизованный основной портрет с эталоном стиля.
4. Сразу после готовности автоматически установить новый комплект. Подтверждение пользователем не требуется.
5. В фоне создать эмоции; до их готовности использовать новый нейтральный портрет.

Пока основного портрета нет, сохраняется прежний выбранный образ. Ошибка проверки или стилизации не меняет его.
Если результат не нравится, пользователь загружает другое изображение. При нескольких последовательных загрузках
устаревшее задание не должно поздно заменить более новый выбор: применяется идентификатор/версия актуального запроса.

### Последовательность реализации

1. Выбрать художественный стиль и провайдера; подготовить эталоны и два готовых пользовательских комплекта.
2. Добавить модель комплектов, выбор пользователя, реестр NPC и снимки сцен. Учесть старые диалоги:
   NPC восстановить из сообщений и сводки, изображения пометить отсутствующими; не запускать массовую
   генерацию всей старой истории автоматически.
3. Расширить контракт LLM и парсеры: объявление внешности нового NPC, стабильные ссылки, коды эмоций,
   эмоция пользователя и сведения о составе сцены. Сохранить существующий текстовый стриминг.
4. Добавить адаптер внешнего генератора, таблицы заданий/outbox, очередь и processor в worker.
5. Реализовать сохранение в R2, зависимости, восстановление заданий и межпроцессные уведомления.
6. Добавить визуальные DTO, загрузку состояния, SSE обновления и клиентское отображение.
7. Добавить выбор готового образа в личном кабинете и обновление аватаров во всех диалогах.
8. Проверить сценарии ниже и обновить описание реализованного поведения в документации.
9. Отдельным следующим этапом добавить загрузку и автоматическую стилизацию собственного изображения.

### Критерии готовности

- Готовый образ выбирается в личном кабинете; каталог не ограничен двумя значениями в схеме.
- Сценарий без заранее заданного NPC работает; первый и последующие NPC получают образы динамически.
- NPC без имени, роли и биографии поддерживается; возвращающийся персонаж использует тот же комплект.
- Одновременные запросы и повторная доставка заданий не создают несколько комплектов одного NPC.
- Известная эмоция выбирает нужное изображение; неизвестная или ещё не готовая использует нейтральное.
- Пользователь не выбирает эмоцию вручную; вычисленное выражение обновляет его исходную реплику.
- Иллюстрация ставится в очередь только для `sceneUpdate`; поздний результат попадает к своей сцене.
- Смена пользовательского образа обновляет аватары прошлых сообщений, но сохраняет готовые сцены.
- Долгая генерация, ошибка провайдера и ожидание портретов не блокируют отправку текста после `turnDone`.
- Перезапуск worker и разрыв SSE не теряют задания и готовые изображения.
- Worker и HTTP-процесс могут работать раздельно; уведомления доставляются через межпроцессный канал.
- Удалённый диалог не получает поздние результаты; удаление не повреждает общие материалы.
- Чужие личные изображения недоступны; истечение подписанного URL устраняется получением нового URL.
- Будущий этап загрузки отклоняет неподходящие изображения и автоматически применяет подходящий результат
  без подтверждения, сохраняя правильный порядок конкурирующих загрузок.

Проверки должны охватывать контракты и существенные сценарии восстановления/конкуренции, а также отображение
поздних изображений в интерфейсе. Код эмоций и ссылки на NPC проверяются детерминированно; точное сходство лиц
не является критерием готовности.
