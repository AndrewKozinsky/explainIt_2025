# Изображения в диалогах с ИИ

## Реализованное поведение

Сервер генерирует спрайты NPC и иллюстрации сцен через OpenAI и универсальный
[`imageGenerationProviderAdapter`](../imageGenerationProviderAdapter.md).
Сохранение сообщений/заданий/outbox транзакционное; publisher передаёт задания в BullMQ, отдельный worker
готовит референсы и публикует исходники в R2/БД. Реализованы авторизованный REST-снимок, Redis/SSE-сигналы
и очистка изображений. Картинки не блокируют текст, `turnDone` завершает только текстовый ход.
Клиентское отображение ещё не подключено; клиент в этом серверном изменении не менялся.

Основной текстовый контракт: [`aiDialogue.md`](aiDialogue.md).
Пользователь сообщил, что миграция применена, общие изображения загружены, а старых BFL-заданий нет:
генерации не запускались. Feature не поддерживает старое BFL polling и не переносит старые модели в OpenAI.
FLUX-поставщик сохраняется только в универсальной infrastructure.

## Настройки новых заданий

`server/src/features/aiDialogue/aiDialogueVisualConfig.ts`:

- `AI_DIALOGUE_IMAGE_MODEL`: `gpt-image-2.5-sunburst-2026-09-08`, фиксированный снимок модели;
- `AI_DIALOGUE_IMAGE_QUALITY`: `low` для тестов, позже можно поставить `medium` или `high`;
- `AI_DIALOGUE_IMAGE_FORMAT`: `png`;
- `AI_DIALOGUE_EMOTION_SHEET_SIZE`: 960×720 (ячейка 240×240);
- `AI_DIALOGUE_SCENE_SIZE`: 1152×576;
- `AI_DIALOGUE_EMOTION_LAYOUT_VERSION`: `emotion-grid-4x3-v1`;
- `AI_DIALOGUE_VISUAL_STYLE_PROMPT`: единая художественная инструкция.

Размер отображаемого аватара 120×120 не задаёт размер генерации. Для листа 4×3 с такими ячейками потребовалось бы
480×360, что не допускается API. 1000×500 для сцены также не допускается: стороны должны быть кратны 16,
площадь — не меньше 655360. Выбраны минимальные разрешённые размеры с точными пропорциями 4:3 и 2:1.
Ограничения проверены по [официальным параметрам OpenAI](https://developers.openai.com/api/docs/guides/image-prompting).
Адаптер не округляет неподдерживаемые размеры молча: неверная настройка отклоняется до платной отправки.

Модель, размер, качество, формат, стиль, описание внешности/сцены и ключи референсов копируются в
`ImageGenerationJob.input` при создании. Worker читает этот снимок, а не текущие настройки.
Изменение настройки действует только на новые задания. Готовые изображения не перегенерируются.
Исходные байты сохраняются в R2 без уменьшения или перекодирования. Автоматической оценки художественного качества нет.

## Общий портрет и художественные референсы

Фактические ключи из visual config:

- пользователь: `ai-dialogue-images/shared/user-avatar.jpg`;
- стиль портрета NPC: тот же `ai-dialogue-images/shared/user-avatar.jpg`;
- стиль сцены: `ai-dialogue-images/shared/style-scene.jpg`.

Это ключи объектов, не URL и не локальные пути. Бакет выбирается существующим `CLOUDFLARE_S3_BUCKET_NAME`.
Локальный исходник общего портрета: `server/assets/aiDialogue/user-avatar.jpg`, промпт рядом в `.prompt.txt`.
Повторной загрузки или автоматической генерации эталонов нет. Приватный R2 читается серверным токеном.
Для замены эталона нужно загрузить подходящий PNG/JPEG/WebP и обновить реальный ключ в visual config.
Общие ресурсы хранятся вне generated-префикса и не удаляются с диалогом.

Стиль: современная редакционная иллюстрация с влиянием графического романа, взрослые реалистичные пропорции,
мягкий контур, лёгкая фактура и тени, спокойная умеренно тёплая палитра, читаемые лица.
Исключаются фотореализм, гротеск, 3D, текст, рамки, UI и водяные знаки.
Из стилевого референса заимствуется оформление, не персонаж или композиция.
Стиль не имеет отдельной таблицы/версии: версия layout относится только к геометрии спрайта.

## NPC, эмоции и спрайт

NPC уникален по `(dialogueId, npcId)`; имя/роль не определяют идентичность. `AiDialogueCharacter` хранит
внешность независимо от компакции текста. Новый NPC создаёт одно задание emotionSheet.
При возвращении используется существующий спрайт; завершение встречи не удаляет NPC.
`npcActions` связывается с character_id этого диалога; npcId и emotion остаются в payload.
Пользовательские/системные события, включая sceneUpdate, имеют character_id=null.

Порядок `aiDialogueEmotions` задаёт строки сетки 4×3:

1. `neutral`, `happy`, `sad`, `angry`;
2. `surprised`, `confused`, `worried`, `embarrassed`;
3. `thoughtful`, `skeptical`, `relieved`, `encouraging`.

За один запрос получается один лист: голова и плечи того же взрослого NPC во всех 12 квадратных ячейках.
Одинаковы одежда, ракурс, свет и фон, меняется выражение; нет текста, рамок, отступов и разделителей.
Промпт фиксирует row-major порядок и bounding boxes в нормализованных координатах 0–1000.
Неизвестная эмоция нормализуется в neutral. Новая реплика не меняет эмоции старой.
Будущий клиент показывает нужную ячейку через `background-size: 400% 300%` и background-position в области 120×120.
Отдельных файлов/таблиц для каждой эмоции нет. Точное художественное соблюдение сетки проверяется пользователем;
сервер проверяет геометрию всего файла, а не распознаёт выражения лиц.

## Текстовый контракт и сцены

Новый NPC содержит внешность на английском:

```text
npcActions|stranger_1|Alex|passer-by|worried
appearance:
adult with short dark hair and a green raincoat
speech:
Are you lost?
Вы заблудились?
```

Известный npcId переиспользуется; повторная внешность игнорируется при сохранении.
Сцена создаётся только для sceneUpdate, включая начальное событие, если оно есть в ответе:

```text
sceneUpdate
You enter a dental office.
Вы входите в стоматологический кабинет.
participants:dentist_1
visual:The learner stands by the door while the dentist turns to greet them.
```

Парсер возвращает `{ events, visualMetadata }`; appearance/participants/visual не становятся отдельными сообщениями.
Неизвестные npcId отбрасываются, NPC ниже по тексту того же хода поддерживаются.
Новая эмоция, worldEvent, появление/уход NPC сами по себе не создают иллюстрацию.

Отдельной таблицы сцен нет: payload sceneUpdate хранит content/translation и visualDescription/participantNpcIds.
Задание фиксирует message_id, dialogueId, описание момента, NPC и их внутренние ID.
Поздняя готовая картинка прикрепляется к исходному сообщению, не к последнему состоянию диалога.
Worker проверяет владельца сообщения и соответствие NPC снимку.

Порядок референсов сцены: пользователь → нейтральные ячейки NPC → эталон стиля. Пользователь присутствует в кадре,
но не входит в список NPC. Worker ждёт спрайты NPC; отсутствующая/failed зависимость становится ошибкой картинки,
не текста. Верхняя левая neutral-ячейка извлекается в памяти и при необходимости увеличивается до 256×256
для существующего валидатора референсов. Исходник в R2 не меняется.
Референсы передаются через общий контракт байтов/MIME и OpenAI images.edit; публичные URL для них не нужны.
Всего не больше 16 референсов. angleSheet существует в типах, но этот pipeline его не генерирует.

## Хранение и очередь

Таблицы: `AiDialogueCharacter`, `AiDialogueImage`, `ImageGenerationJob`, `ImageGenerationOutbox`.
AiDialogueImage хранит владельца-NPC или сообщение-сцену, тип, раскладку, ключ R2, MIME, ширину и высоту.
Job хранит цель, JSON input, статус, attempts/error; outbox — надёжную передачу задания в очередь.
Уникальны NPC пары, dedup_key задания, ключ ассета и job_id outbox; SQL CHECK требует ровно одного владельца.
Каскадное удаление владельца удаляет ассеты/задания в БД.

Транзакция хода → outbox → BullMQ → worker → общий адаптер/OpenAI → проверка оригинала → R2 → ready в БД.
Publisher HTTP каждые 5 секунд берёт до 20 записей. Детерминированный BullMQ jobId защищает от повторной доставки.
Processor с concurrency=1 откладывает ожидание зависимостей/ошибки хранилища, освобождая слот.
Статусы: queued, waitingDependencies, generating, ready, failed. attempts считает ошибки обработки.
Генерация не запускается из SSE chunks/превью и не занимает ActiveAiDialogueGenerationRegistry.

## Публикация и окна сбоев

`submitImageGenerationRequest` валидирует общий запрос, затем `claimSubmission` атомарно переводит queued или
waitingDependencies в generating и добавляет только `resultS3Key` в существующий JSON input.
CAS сравнивает исходный input и статус; проигравшая или неопределённая попытка claim не отправляет запрос.
Параметры генерации не меняются. Новая миграция не нужна; применённые миграции/схема не редактировались.
Прежние provider_request_id/provider_polling_url остаются в схеме, но OpenAI feature не заполняет их.

Ключ резервируется до платной отправки:
`ai-dialogue-images/generated/<region>/<mode>/job-<id>/<uuid>.<extension>`.
После ответа worker полностью декодирует PNG/JPEG/WebP, проверяет MIME, точные пиксели/формат снимка,
отсутствие анимации/EXIF-поворота, максимум 32 MiB и 16 млн пикселей. Оригинал не меняется.
PUT ограничен 60 секундами; метаданные и ready сохраняются атомарно после upload.
Перед публикацией повторно проверяется существование и статус задания; удалённый диалог не восстанавливается.

OpenAI Images API возвращает готовые байты. Адаптер не имитирует внешний polling/recovery,
использует тайм-аут 180 секунд и `maxRetries: 0`. Повтор очереди не означает повтор генерации.

- Сбой до claim: оплачиваемый запрос не отправлен; повтор подготовки допустим.
- Сбой/потеря подтверждения claim: следующая обработка читает состояние, а не повторяет POST.
- Тайм-аут, потерянный ответ или сбой после получения байтов до сохранения R2: если файла нет по ключу,
  результат нельзя восстановить через Images API. Job остаётся generating с безопасной ошибкой и
  UnrecoverableError в очереди; нужна ручная проверка. Автоматической новой генерации нет.
- PUT мог пройти, но подтверждение потеряно: worker читает тот же ключ и завершает публикацию.
- Сбой между upload и коммитом БД, включая откат: оригинал активного задания сохраняется в R2,
  worker повторяет только запись метаданных из этого файла, без PUT и без OpenAI.
- Потеря подтверждения коммита: проверяется существующий AiDialogueImage; опубликованный объект не удаляется.
- 404 чтения checkpoint означает отсутствие; 403, сеть и недоступная БД не считаются отсутствием файла,
  повторяется только восстановление хранилища. generating не переводится в failed из-за исчерпания таких повторов,
  чтобы не потерять доступный для восстановления оригинал.
- Удаление владельца во время upload/коммита: объект больше не публикуется; адресная/фоновая очистка убирает остаток.

Нет гарантии exactly-once оплаты. Отключённые повторы предотвращают автоматическую повторную отправку,
но ручной сброс в queued может повторно оплатить уже принятую генерацию. Снимок/ошибку/ключ необходимо проверить
до любых ручных действий. Автоматического reset, перенаправления модели или массовой перегенерации нет.
Документированный контракт: [OpenAI Images API](https://developers.openai.com/api/docs/guides/image-generation).

## REST и SSE

`GET /api/ai-dialogue/:id/visuals`: авторизация до подписания URL, 404 для отсутствующего, 403 для чужого диалога;
`Cache-Control: private, no-store`. Ответ:

- dialogueId, userAvatarUrl, urlsExpireAt;
- characters: id, npcId, name/role, generationStatus, emotionSheet;
- scenes: messageId, generationStatus, image;
- image/emotionSheet: id, url, mimeType, width, height, layoutVersion (null для сцены).

Нет отдельных ключей R2, промптов, ошибок, attempts, внешних реквизитов или байтов.
Непривязанные/ещё не готовые ассеты равны null; владельцы без заданий имеют generationStatus=null.
Чтение БД — RepeatableRead; затем подписываются URL на 6 часов, urlsExpireAt — через 5 часов.
Подписывание не проверяет наличие R2-файла. NPC сопоставляется через npcId, сцена — через messageId.

Worker посылает только `{ jobId }` через Redis-канал `ai-dialogue-visuals:<mode>:<region>`.
HTTP bridge перечитывает владельца/ready/failed и отправляет технический visualsChanged в локальную SSE-шину.
Неопределённый generating не создаёт terminal-уведомления. Ошибка картинки не создаёт turnError.
Redis Pub/Sub — best effort, не durable outbox; источник истины REST/БД.
Будущий клиент перечитывает visuals при подключении, visualsChanged, новых NPC/сценах, истечении URL и периодически
при незавершённых заданиях. Reconnect Redis также сигнализирует активным потокам перечитать снимок.
SSE подписывается до replay, но буферизует события до проверки владельца; отказ/отключение снимает подписку.

## Очистка

DELETE проверяет владельца, читает ключи и каскадно удаляет диалог одной транзакцией. Только после коммита
пытается удалить R2; сбой очистки не отменяет DELETE. Каждый адресный DELETE R2 ограничен 10 секундами.
Общий портрет и эталоны исключены.

HTTP каждые 30 секунд обходит страницу из 25 объектов своего REGION/MODE-префикса.
Непривязанные файлы удаляются не раньше суток после LastModified. Курсор сбрасывается при конце/ошибке/restart.
Перед удалением в RepeatableRead проверяются ссылки AiDialogueImage, активность задания и ключи в input
активных заданий, включая resultS3Key. При недоступной БД файл сохраняется.
HTTP/worker обязаны иметь одинаковый namespace/бакет; один namespace должен соответствовать одной БД.
Невалидные/чужие ключи не удаляются. Общий обход старого префикса без namespace запрещён;
такие объекты удаляются только по подтверждённым ключам своей БД, ошибки требуют адресного ручного повтора.
R2-токен production должен разрешать ListObjectsV2/DeleteObject.

## Проверка общих ресурсов и запуск

До включения worker выполнить из server с полным серверным окружением:

```bash
npm run check:ai-dialogue-image-assets
```

CLI использует MainConfigModule (`getEnVariables()` → `get()`), только читает R2, не запускает HTTP/worker,
Prisma/Redis, очереди, очистку или генерацию. Контекст/S3-клиент закрываются после проверки.
Проверяет три ключа, полностью декодируя PNG/JPEG/WebP: максимум 32 MiB, 16 млн пикселей, минимум 256×256,
без анимации/поворота. Это не оценка пригодности лица/художественного стиля.
JSON содержит ready и assets с asset/key/status; ready-ассеты дополнены width/height/mime.
Статусы: ready, unconfigured, unavailable (чтение), invalid (формат); код выхода 0 только при полной готовности.
Ошибки отдельных файлов не прекращают остальные проверки; секреты/байты/SDK-ответы не выводятся.

REGION/MODE в localdev задаёт Docker Compose, чтения одного env-файла на машине недостаточно.
Для уже запущенного контейнера:

```bash
docker exec explainserverlocaldev npm run check:ai-dialogue-image-assets
```

Основной worker ради проверки ресурсов запускать нельзя: OPENAI_API_KEY разрешает платные генерации накопленных заданий.
Используется существующий `get().openAI.apiKey`, без новой env-переменной. Доступ аккаунта к выбранной модели
и ресурсам R2 нужно проверить отдельно; наличие ключа само по себе его не доказывает.

## Проверки и оставшиеся шаги

Сборка, TypeScript и изолированные тесты проверяют provider/worker, конкурентный claim, точные параметры,
референсы, оригинальные байты, отсутствие автоматических повторов, R2/DB crash windows и регистрацию Nest.
Внешние SDK/HTTP, БД и R2 подменены. Платные вызовы и настоящие загрузки/удаления не выполнялись,
миграции не менялись, приложение/worker не запускались, коммит не создан.

`npm run build`, `npx tsc --noEmit --incremental false`, `npm test`, `git diff --check` проходят:
262 теста в 32 наборах, 14 существующих тестов в 9 наборах пропущены. Регистрация в настоящем Nest-контексте
и отсутствие повтора 503 в настоящем SDK проверены с подменёнными конфигурацией/HTTP, без генерации.

После просмотра серверных файлов отдельно согласовать платный smoke test. Он должен визуально проверить
12 эмоций/сетку, узнаваемость NPC, участника-пользователя и общий стиль сцен. Затем подключать клиент.
Выбор пользовательского аватара, загрузка/стилизация фотографии, бюджеты и дополнительные листы ракурсов
остаются вне текущего объёма.
