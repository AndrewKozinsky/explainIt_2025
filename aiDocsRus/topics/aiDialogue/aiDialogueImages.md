# Изображения в диалогах с ИИ

## Назначение и статус

**Статус: согласованный план, ещё не реализован.**

Этот документ описывает аватары участников и иллюстрации сцен в `AiDialogue`.
Основное поведение текстового диалога, его SSE-поток и хранение сообщений описаны в
[`aiDialogue.md`](aiDialogue.md). Визуальные материалы помогают погрузиться в разговор, но не блокируют
отправку, генерацию и отображение текста.

## Согласованные правила

- Пользователь выбирает готовый комплект аватаров. Первоначально доступны мужской и женский варианты;
  каталог должен поддерживать больше готовых и будущие личные комплекты.
- NPC появляются динамически в конкретном диалоге. Сценарий может не задавать персонажей заранее.
- При первом появлении NPC создаётся его внешний образ. Когда персонаж возвращается в том же диалоге,
  используется уже созданный комплект.
- Имя, роль и биография NPC необязательны. Обязательны только `npcId` в рамках диалога и краткое описание внешности.
- Эмоции определяет ИИ. Пользователь не выбирает их вручную.
- Иллюстрация ставится в очередь только после сохранения `sceneUpdate`.
- Все файлы хранятся в Cloudflare R2.
- Небольшое расхождение внешности на разных изображениях допустимо. Результаты не перегенерируются ради
  точного сходства лица.
- Смена образа пользователя обновляет его аватар возле всех прошлых реплик. Уже созданные сцены не меняются.
- Приложение не ведёт расчёт стоимости, бюджетов или квот на генерацию. Технические лимиты, повторы и тайм-ауты
  остаются нужны для стабильной работы.

## Персонажи

Персонаж существует в области одного диалога. Его ключ — `(dialogueId, npcId)`, а не имя или профессия.
Это позволяет использовать два разных персонажа с одинаковой ролью и сохранять одного персонажа при повторной
встрече. Реестр NPC хранится отдельно от сообщений и `summary`: компакция истории не должна терять внешность,
статус генерации или ссылки на изображения.

LLM получает реестр уже известных NPC. При новом персонаже он возвращает новый `npcId` и описание внешности;
сервер создаёт запись один раз. При повторном появлении сервер не переписывает описание случайно изменившимся
текстом LLM. Завершение встречи с NPC не удаляет его из реестра.

### Новый NPC

1. Сервер сохраняет NPC и описание внешности.
2. Текстовая реплика сразу приходит на клиент, который показывает заглушку вместо аватара.
3. В очередь добавляется основной нейтральный портрет с эталоном стиля.
4. После сохранения портрета в R2 связанные реплики обновляются.
5. В фоне создаются нужная эмоция, остальные эмоции и, при необходимости, ракурсы.

До готовности конкретной эмоции используется нейтральный портрет этого NPC; до готовности портрета — общая заглушка.
Повторное появление не создаёт второй комплект или второе задание.

## Образы пользователя и стиль

`AvatarSet` — выбранный пользователем комплект: основной нейтральный портрет, эмоции, необязательные ракурсы,
описание и версия стиля. Пользователь хранит ссылку на комплект, поэтому схема не ограничена enum со значениями
«мужской» и «женский». Общий комплект может использоваться многими пользователями.

Стиль задаёт версионируемый набор эталонных картинок и краткое описание палитры, линий, освещения, пропорций
и детализации. Нужны как минимум эталон портрета и эталон сцены. Основной портрет становится референсом для эмоций;
нельзя строить цепочку из предыдущих эмоций, поскольку внешность будет постепенно меняться.

Ракурсы — анфас, профиль, три четверти, сзади и фигура — поддерживаются в модели, но генерируются только когда нужны.
Не требуется заранее готовить все комбинации ракурсов и эмоций.

Для сцены генератор получает эталон стиля, основные портреты пользователя и участников, описание момента и,
при наличии, подходящие ракурсы или референс помещения. Предыдущая сцена может быть дополнительным референсом,
но не заменяет основные портреты.

## Эмоции

Начальный словарь: `neutral`, `happy`, `sad`, `angry`, `surprised`, `confused`, `worried`, `embarrassed`,
`thoughtful`, `skeptical`, `relieved`, `encouraging`. Его необходимо окончательно зафиксировать до подготовки
готовых комплектов.

ИИ возвращает код эмоции при генерации фразы. Для блока используется последняя возвращённая эмоция; отдельная модель
смены эмоций внутри `actions` не требуется. Каждое сохранённое сообщение сохраняет свой код, поэтому новая реплика
не изменяет старые аватары.

Эмоцию пользователя ИИ определяет по контексту. Она приходит как отдельная визуальная метаинформация со ссылкой
на исходное сообщение, не создаёт новое `userActions` и не меняет отправленный текст. Пока обновление не пришло,
показывается нейтральный пользовательский аватар. Неизвестный код нормализуется до `neutral`.

## Сцены

Каждый сохранённый `sceneUpdate` создаёт снимок сцены и одно задание на иллюстрацию. Начальная сцена иллюстрируется,
только если LLM отправила начальный `sceneUpdate`. Появление NPC, эмоция, `worldEvent` или уход пользователя сами
по себе не запускают изображение.

Снимок фиксирует исходное сообщение, текст ситуации, участников, версии их образов, стиль, позы, одежду и важные
предметы. Его нельзя строить из текущего состояния worker: пока задача ждёт, диалог может перейти в другую сцену.
Если свободного текста `sceneUpdate` недостаточно, контракт LLM должен возвращать визуальное состояние сцены либо
сервер извлекает его из подтверждённых событий того же хода.

Задание может ожидать основные портреты участников. После исчерпания попыток оно завершается ошибкой без влияния
на текстовый диалог. Готовое изображение привязывается к своему `sceneId` и появляется возле соответствующего
`sceneUpdate`, даже если пользователь уже находится дальше по истории.

## Хранение

| Сущность | Назначение |
| --- | --- |
| `AiDialogueVisualStyle` | Версия стиля, описание и эталоны |
| `AvatarSet` | Общий или личный комплект пользователя |
| `User.avatar_set_id` | Текущий образ пользователя |
| `AiDialogueCharacter` | NPC конкретного диалога и его основной портрет |
| `AiDialogueScene` | Неизменяемый снимок `sceneUpdate` и участников |
| `AiDialogueMessageVisual` | Эмоция сообщения, в том числе определённая для пользователя |
| `ImageAsset` | Изображение, назначение, версия, ключ R2, MIME и размеры |
| `ImageGenerationJob` | Вход, зависимости, статус, попытки, провайдер, модель и ошибка/результат |
| `ImageGenerationOutbox` | Надёжная передача задания в очередь |

Нужны уникальные ограничения для `(dialogue_id, npc_id)`, снимка сцены и варианта изображения. Вход задания
фиксируется при его создании: worker не подменяет стиль или пользовательский образ текущими значениями.

## Генерация и доставка

Используются существующие BullMQ, Redis, отдельный worker и Cloudflare R2. В транзакции сохраняются снимок,
задание и запись outbox; диспетчер передаёт задание в BullMQ с безопасным повтором. Нельзя полагаться только
на `fire-and-forget` из HTTP-процесса.

Статусы `queued`, `generating`, `ready`, `failed` хранятся в БД. Для зависимостей предусмотрен отдельный статус
ожидания. Ограничены параллельность, тайм-аут и число попыток. Идентификатор внешнего запроса сохраняется, чтобы
после перезапуска сначала проверить уже отправленную генерацию.

Генерация запускается только после сохранения событий, никогда не из SSE `chunk` или клиентского превью.
Она не занимает `ActiveAiDialogueGenerationRegistry`, а `turnDone` завершает только текстовый ход.

Перед публикацией проверяются декодирование файла, MIME и размеры. Результат готов только после сохранения
в R2 и записи метаданных. Генератор скрыт за адаптером: он получает описание и референсы, а возвращает файл
или внешний асинхронный запрос. Конкретный провайдер будет выбран отдельно между FLUX 3 Image, OpenAI GPT Image
и Comfy API после проверки на выбранном стиле.

Техническое событие, например `visualAssetUpdated`, передаёт готовность изображения по SSE. Оно не является
`AiDialogueMessage`: не влияет на следующий ход, промпт и компакцию. Так как текущая SSE-шина работает в памяти,
worker уведомляет HTTP-процесс через Redis или другой межпроцессный канал. БД остаётся источником состояния,
поэтому переподключение не теряет готовые материалы.

## Доступ и удаление

В БД хранится ключ R2, а подписанный URL выдаётся при чтении после проверки доступа. Общие комплекты и эталоны
могут переиспользоваться. Личные изображения, NPC и сцены доступны владельцу диалога.

Удаление диалога отменяет задания и удаляет его личные материалы. Worker проверяет существование объекта перед
публикацией, чтобы поздний результат не восстановил удалённый диалог. Общие материалы и личный образ пользователя,
который ещё используется в других диалогах, не удаляются.

## Будущая загрузка фотографии

Поддержка личных `AvatarSet` закладывается сразу, а интерфейс загрузки реализуется отдельным этапом.

1. Проверить файл, размер, тип и декодирование.
2. Проверить содержимое: нужен один подходящий человек или персонаж. Дом, пейзаж, группа без явного главного лица
   и другие неподходящие изображения отклоняются с понятной ошибкой.
3. Для подходящего входа создать стилизованный основной портрет.
4. После готовности автоматически установить новый комплект без подтверждения.
5. Подготовить эмоции в фоне.

До готовности сохраняется предыдущий аватар. Если пользователь загружает несколько файлов подряд,
устаревшая задача не может поздно применить старый результат.

## Последовательность реализации

1. Выбрать стиль, провайдера и подготовить два стартовых комплекта.
2. Добавить модель образов, персонажей, сцен, заданий и outbox; старые диалоги не генерировать массово.
3. Расширить контракт LLM для NPC, эмоций и визуального состояния сцены.
4. Добавить адаптер генератора, очередь, worker, R2 и межпроцессные уведомления.
5. Добавить DTO, REST/SSE-снимок визуального состояния и отображение в клиенте.
6. Добавить выбор пользовательского комплекта в личном кабинете.
7. Отдельно реализовать загрузку и автоматическую стилизацию личного изображения.
