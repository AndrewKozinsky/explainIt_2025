# Профиль пользователя: пол и аватар

Реализованы серверные маршруты и клиентская форма пола/аватара с автосохранением.
Форма находится в `_pages/me/UserProfileForm` и показана перед выходом из личного кабинета.
Клиентские репозитории, сервис, фасад и поведение формы описаны в [`clientUserData.md`](clientUserData.md).
Изображения ИИ-диалогов пока не изменены.
Диалоги продолжают использовать общий портрет `ai-dialogue-images/shared/user-avatar.jpg`.

## База данных

Источник схемы — `server/src/db/dbConfig/dbConfig.ts`. Команда `npm run generatePrismaFile`
создаёт `server/prisma/schema.prisma`; затем обновляются Prisma-типы.
Миграция `20261012120000_add_user_profile` добавляет в `User`:

- `gender`: enum `UserGender` (`MALE`, `FEMALE`), по умолчанию `MALE`;
- `avatar_preset_id`: nullable string, по умолчанию `male-1`;
- `avatar_s3_key`: nullable string, ключ собственной фотографии в R2.

Существующие пользователи получают `MALE`/`male-1`. SQL CHECK требует ровно один источник аватара
и проверяет ID готовых вариантов. Пол можно менять независимо от текущей картинки.
Пол готового аватара задаётся в серверном каталоге, не в метаданных файла.

## Готовые варианты и хранение

Каталог: `server/src/features/user/avatarPresets.ts`. Изображения загружаются в R2 отдельно:

| ID | Пол | Ключ объекта R2 |
|---|---|---|
| male-1 | MALE | user-avatars/shared/male-1.jpg |
| male-2 | MALE | user-avatars/shared/male-2.jpg |
| female-1 | FEMALE | user-avatars/shared/female-1.jpg |
| female-2 | FEMALE | user-avatars/shared/female-2.jpg |

Используется существующий `CLOUDFLARE_S3_BUCKET_NAME` и `CloudflareS3Service`.
Если формат или ключ подготовленного файла меняется, нужно обновить каталог.
Общие изображения не удаляются при изменении профиля.
Фотографии сохраняются по уникальным ключам `user-avatars/uploads/<region>/<mode>/<userId>/<uuid>.webp`.
Каждой паре REGION/MODE в бакете должна соответствовать одна БД; очистка не затрагивает другие пространства.

## REST

Модуль: `server/src/routes/user/user.module.ts`. Все маршруты защищены `CheckSessionCookieGuard`:

| Метод и путь | Вход / результат |
|---|---|
| GET /api/user/me | Текущий `UserOutModel` |
| GET /api/user/avatar-presets | Четыре общих варианта: `id`, `gender`, `avatarUrl`, `avatarUrlExpiresAt` |
| PATCH /api/user/me | JSON с `gender` и/или `avatarPresetId`; обновлённый `UserOutModel` |
| POST /api/user/me/avatar | Multipart с одним полем файла `file`; обновлённый `UserOutModel`, HTTP 200 |

Пустой PATCH, null и неизвестные поля отклоняются. Выбор готового варианта атомарно устанавливает
его ID и пол, даже если передан другой `gender`, и очищает ключ собственной фотографии.
Изменение только `gender` сохраняет картинку. Загрузка фотографии сохраняет текущий пол.
User ID берётся исключительно из сессии.

`UserOutModel` включает `gender`, `avatarPresetId` (null для фотографии), `avatarUrl`, `avatarUrlExpiresAt`
в дополнение к прежним полям. Эти данные также возвращаются при регистрации, входе и OAuth через
`UserQueryRepository`. Ключи фотографий, пароли и другие внутренние поля наружу не передаются.
URL подписываются на шесть часов, срок обновления объявляется через пять часов.
Ответы маршрутов профиля имеют `Cache-Control: private, no-store`.

`GET /api/auth/me` удалён без alias. Клиентское чтение пользователя переведено на `/api/user/me` через `UserApi`/`UserService`.
Контекст и `UserQueryFacade` используют доменный ключ `userQueryKeys.me()`; см. [`clientUserData.md`](clientUserData.md).

## Обработка фотографий

`ImageProcessingService` в `server/src/infrastructure/imageProcessing` — универсальный инструмент:
`inspect` читает метаданные; `transform` принимает выбранные вызывающим кодом параметры ориентации,
размера, формата, качества, лимита пикселей и тайм-аута. Сервис не содержит правил аватаров и не работает с R2.

Правила задаёт `UploadUserAvatarHandler` и `userAvatarConfig.ts`:

- файл до 30 MiB, изображение до 80 миллионов пикселей;
- реальный JPEG/PNG/WebP, корректное декодирование, без анимации; имя файла и присланный MIME не определяют формат;
- EXIF-поворот учитывается до уменьшения;
- меньшая сторона уменьшается до 512 пикселей (`fit: outside`), пропорции и всё содержимое сохраняются;
- маленькие изображения не увеличиваются, обрезки и ИИ-стилизации нет;
- результат — WebP с quality 85; EXIF/GPS не копируются;
- преобразование ограничено 15 секундами, PUT в R2 — 60 секундами.

Nginx разрешает тело до 31 MiB только на `/api/user/me/avatar`, оставляя запас для multipart.
На остальных маршрутах прежний лимит 10 MiB сохраняется.

## Замена и очистка

`UserRepository.updateProfile` использует транзакцию и `SELECT ... FOR UPDATE`, чтобы конкурентные
замены прочитали фактическую предыдущую фотографию и независимо сохранили изменения пола.
Сначала создаётся уникальный файл в R2, затем сохраняется профиль; прежний файл удаляется после коммита.
При неопределённом результате PUT/коммита новый файл сразу не удаляется: он мог уже стать действующим.

`CleanupUserAvatars` каждые 30 секунд читает страницу из 25 объектов своего upload-префикса.
Непривязанные файлы удаляются не раньше суток после LastModified. Перед каждым удалением проверяется
текущая ссылка в `User`; при недоступной БД файл сохраняется. Ошибка удаления не отменяет сохранение профиля.
Курсор сбрасывается при конце обхода/ошибке; при остановке приложения новые удаления не начинаются.
R2-токен должен разрешать ListObjectsV2 и DeleteObject в дополнение к чтению и записи.
Клиент не может повторно привязать произвольный upload-ключ: API принимает только ID готового варианта или новый файл.

## Проверки и следующий этап

`npm test` проверяет профиль, маппинг, обработку изображений и очистку с подменёнными БД/R2.
`npm run test:user-profile` запускает настоящий Nest-контекст и HTTP/multipart/OpenAPI-проверку с подменёнными
БД и R2; использует временный локальный HTTP-порт. Приложение и worker с рабочими настройками не запускаются.
Миграция, значения по умолчанию для существующих/новых пользователей, SQL CHECK и восемь конкурентных
замен через настоящий Prisma дополнительно проверены в отдельном временном PostgreSQL-контейнере.
Рабочая БД и файлы R2 этой проверкой не изменялись.

Перед запуском обновлённого сервера применить миграцию через `npm run migrate:deploy`
в окружении нужной БД и перезагрузить Nginx с обновлённой конфигурацией.
Клиентские модели/мапперы, форма пола/аватара/загрузки и обновление истёкших ссылок подключены.
Следующий этап: персональный аватар в ИИ-диалогах.
